## 1. Философия и позиционирование (подтверждение решений D4)

**Название: Weave.** Расширение `.wv`, компилятор `weavec`, CLI `weave`, манифест `weave.toml`, реестр `weave.dev`. Принято без изменений [D4 §12.1].

**Миссия:** память- и конкурентность-безопасность уровня Rust без «налога на async», при этом доступность уровня Go без отказа от sum types, дженериков и структурной конкурентности. Ниша выбрана по методу D1 §6: успешный язык решает **одну** структурную проблему, которую индустрия доказуемо не решила конвенциями. Проблема Weave: *Rust и Go по отдельности доказали достижимость ownership-безопасности и доступной конкурентности — но ни один мейнстрим-язык не дал обе сразу без ретрофита.*

**Пять ранжированных приоритетов** (при конфликте фич побеждает более высокий):
1. Безопасность доказывается компилятором, а не документируется конвенцией.
2. Один очевидный способ выразить семантику (синтаксическая избыточность — прямой налог на тулинг и читаемость [D3 §8.2]).
3. Модель конкурентности и модель памяти — один дизайн, а не две фичи.
4. Метапрограммирование — `comptime` в самом языке; отдельного макроязыка нет.
5. Производительность «хорошая по умолчанию, отличная по запросу»: release соревнуется с C++/Rust; debug компилируется за секунды.

**Чем Weave сознательно НЕ является** [D4 Part 11]: не конкурент Python в ML (нельзя бутстрапнуть научную экосистему) и не конкурент JS в браузере (это монополия канала дистрибуции, а не качества языка). WASM и GPU — таргеты компиляции, а не поле битвы за нишу.

**Отвергнутые альтернативы позиционирования** (для протокола): (а) «универсальный язык всего» — исторически коррелирует с провалом (D1: Ada, Scala-сложность); (б) GC-язык «лучший Go» — не даёт структурного отличия, ради которого мигрируют; (в) чисто функциональный язык — рынок труда [D1 §4.2] показывает разрыв «любят/нанимают».

## 2. Лексическая структура (закрывает часть открытого пункта «полная грамматика»)

### 2.1 Кодировка и идентификаторы
- Исходники — строго UTF-8, BOM запрещён (диагностика с автофиксом).
- Идентификаторы: `XID_Start XID_Continue*` (UAX #31), NFC-нормализация обязательна; **смешение скриптов внутри одного идентификатора — ошибка компиляции** (защита от trojan-source/homoglyph-атак, [D3 §9.5] supply-chain как проблема дизайна языка). Публичные API-имена линтер требует ASCII.
- Стиль (единый, enforced by `weave fmt`/`weave lint`): типы/трейты/варианты `PascalCase`, функции/переменные/модули `snake_case`, константы `SCREAMING_SNAKE_CASE`.

### 2.2 Ключевые слова (v0.1, полный список — 33)
```
fn let mut const type struct enum trait impl pub use as
if else match for while loop break continue return
scope spawn detach on_cancel
comptime unsafe extern effect
true false self Self where from in
```
Зарезервированы для будущих editions (нельзя использовать как идентификаторы): `gpu async await yield macro dyn move ref box try`.
Обоснование резервирования `async/await`: даже при отсутствии function coloring [D4 §12.3] резервирование бесплатно сейчас и дорого потом; `gpu` — Stage 3 [D4 §12.12].

### 2.3 Литералы
- Целые: `123`, `0xFF`, `0o77`, `0b1010`, разделитель `1_000_000`; суффиксы типов `42u8`, `7i64`, `1usize`. Тип по умолчанию `i32` (bidirectional inference уточняет по контексту).
- Плавающие: `1.5`, `2e10`, `1.5f32`; по умолчанию `f64`.
- Строки: `"..."` (escape-последовательности `\n \t \\ \" \u{1F600}`), сырые `r"..."`, `r#"..."#`; многострочные — обычные строки могут содержать перевод строки. Интерполяция: `"user {id} loaded"` — `{expr}` внутри строкового литерала десугарится в вызов `fmt` на comptime (то же ядро, что `weave doc`-примеры; нет отдельного макроса `format!` — приоритет №2 и №4).
- Символ: `'a'` (Unicode scalar value, тип `char`), байтовые строки `b"..."` (тип `Bytes`).
- Комментарии: `//`, `/* */` (вложенные разрешены), doc-комментарии `///` (item) и `//!` (модуль) — парсятся в AST, а не выбрасываются лексером (требование `weave doc` и LSP-hover, [D3 §8.2]).

### 2.4 Операторы и таблица приоритетов (от слабого к сильному)
```
1  =  +=  -=  *=  /=  %=            (присваивание; statement-level, не выражение)
2  or                                (логическое ИЛИ, short-circuit)
3  and                               (логическое И, short-circuit)
4  == != < <= > >=                   (сравнение; НЕ ассоциативно: a < b < c — ошибка)
5  |                                 (битовое ИЛИ)   6  ^   7  &
8  << >>                             9  + -           10 * / %
11 unary: - not & &mut *             12 ?  .await-нет  (постфикс ?: propagation)
13 вызов f(x), индекс a[i], поле x.f, метод x.f(y)
14 пути: module.item, Type.Variant
```
Решения: `and/or/not` словами (читаемость, меньше визуального шума — Go/Rust-опыт показывает, что `&&/||` не несут ценности кроме привычки; конфликт с приоритетом №2 разрешён в пользу единственного варианта — символьные формы `&&/||` **не** поддерживаются). Нессоциативные сравнения — прямой ответ на класс багов C. Присваивание не выражение — исключает `if x = y` класс ошибок.

## 3. Грамматика ядра (EBNF, расширяет [D4 §15.1] до реализуемого объёма)

```ebnf
program      := item* ;
item         := attribute* visibility? (fn_decl | struct_decl | enum_decl | trait_decl
              | impl_decl | type_alias | const_decl | effect_decl | extern_block | use_decl) ;
visibility   := "pub" ;
attribute    := "#[" ident ("(" attr_args ")")? "]" ;            (* #[repr(C)], #[test], #[deprecated] *)

use_decl     := "use" path ("as" ident)? ;                        (* use net.http as h *)
path         := ident ("." ident)* ;

fn_decl      := "comptime"? "fn" ident generics? "(" params? ")"
                ("->" type)? effect_clause? provenance_clause? where_clause? block ;
params       := param ("," param)* ","? ;
param        := ("self" | "mut"? ident ":" type) ;
effect_clause    := "!" effect_set ;
effect_set       := "{" (effect_ref ("," effect_ref)*)? "}" | effect_var ;
effect_ref       := path ;                                        (* fs.Read, db.Write *)
effect_var       := ident ;                                       (* полиморфизм: ! E *)
provenance_clause := "from" ident ("," ident)* ;                  (* §5.4: заимствования результата *)

struct_decl  := "struct" ident generics? where_clause? "{" (field ("," field)* ","?)? "}" ;
field        := visibility? ident ":" type ;
enum_decl    := "enum" ident generics? "{" variant ("," variant)* ","? "}" ;
variant      := ident ("(" field_or_type ("," field_or_type)* ")")? ;
trait_decl   := "trait" ident generics? (":" bound_list)? "{" (fn_sig | fn_decl)* "}" ;
fn_sig       := "fn" ident generics? "(" params? ")" ("->" type)? effect_clause? ;
impl_decl    := "impl" generics? (trait_ref "for")? type where_clause? "{" fn_decl* "}" ;
effect_decl  := "effect" ident "{" ident ("," ident)* "}" ("requires" effect_set)? ;
type_alias   := "type" ident generics? "=" type ;
const_decl   := "const" ident ":" type "=" expr ;
extern_block := "extern" string_lit "{" (fn_sig ";")* "}" ;

generics     := "<" gen_param ("," gen_param)* ">" ;
gen_param    := ident (":" bound_list)? | "effect" ident ;
bound_list   := trait_ref ("+" trait_ref)* ;
where_clause := "where" (type ":" bound_list) ("," type ":" bound_list)* ;

type         := path generics_args? | "&" "mut"? type | "*const" type | "*mut" type
              | "(" type ("," type)* ")" | "fn" "(" (type ("," type)*)? ")" ("->" type)? effect_clause? ;
generics_args := "<" type ("," type)* ">" ;

block        := "{" stmt* expr? "}" ;
stmt         := let_stmt | expr_stmt | item | ";" ;
let_stmt     := "let" "mut"? pattern (":" type)? "=" expr ;
expr_stmt    := expr ;                                            (* точка с запятой: см. §3.1 *)
expr         := literal | path | call | method_call | field_access | index
              | if_expr | match_expr | loop_expr | block | binop | unop
              | scope_expr | spawn_expr | struct_lit | tuple_lit | "(" expr ")"
              | expr "?" ( "context" "(" expr ")" )?
              | "unsafe" block | "comptime" block ;
if_expr      := "if" expr block ("else" (if_expr | block))? ;
match_expr   := "match" expr "{" arm ("," arm)* ","? "}" ;
arm          := pattern ("if" expr)? "=>" expr ;
pattern      := "_" | literal | ident | path ("(" pattern ("," pattern)* ")")?
              | "(" pattern ("," pattern)* ")" | pattern "|" pattern ;
loop_expr    := "loop" block | "while" expr block | "for" pattern "in" expr block ;
scope_expr   := "scope" block ;
spawn_expr   := "spawn" block | "detach" block ;
struct_lit   := path "{" (ident ":" expr) ("," ident ":" expr)* ","? "}" ;
```

### 3.1 Решения по синтаксису и trade-offs
- **Без `;` в конце строк** там, где конец выражения однозначен: правило автозавершения инструкций как в Go/Swift/Kotlin (лексер вставляет терминатор на переводе строки, если токен слева может завершать выражение и токен справа может начинать новое). Явная `;` разрешена. Trade-off: +1 правило в лексере против ежедневного шума; Go доказал надёжность подхода десятилетием практики. Grammar-неоднозначности (унарный минус на новой строке) решаются как в Go: перенос — терминатор, оператор пишется на строке выше.
- Последнее выражение блока без терминатора — значение блока (expression-oriented, как Rust): убирает `return` в 80% функций, ровно один способ вернуть значение из `if/match`-выражений (приоритет №2).
- `match` обязан быть исчерпывающим (compile error) [D4 §12.4]; `_` — явный opt-out.
- Модули = каталоги, без `mod`-деклараций [D4 §12.7]. Файл = под-модуль своего каталога; видимость только `pub`/приватный-для-пакета (двух уровней достаточно; Rust-овские `pub(crate)`/`pub(super)` — источник сложности с малой пользой; при реальной нужде edition-механизм позволит добавить).

## 4. Система типов

### 4.1 Виды типов и семантика значений
Решение [D3 §7.7, Practical conclusion 3]: **value-семантика по умолчанию, решена на уровне системы типов с первого дня** (урок CLR vs JVM/Valhalla — самое дорогое, что можно ретрофитить).
- `struct` — value-тип: хранится inline, `let b = a` — *move* для не-`Copy` типов, побитовая копия для `Copy` (примитивы, кортежи из `Copy`, `#[derive(Copy)]` для мелких struct).
- Куча — явная: `Box<T>` (уникальное владение), `Shared<T>` (иммутабельный refcount, единственный разрешённый межпроцессный тип данных — см. §7.4).
- Никакого наследования; композиция + трейты. Никакого `null`: `Option<T>` [D4 §12.4].
- Целочисленное переполнение: checked в debug (panic), wrapping-запрещён неявно в release — release тоже checked, отключаемо per-block `unsafe { unchecked_add(...) }`. Trade-off: ~1–5% производительности против целого класса CVE; приоритет №1 бьёт №5, а «отлично по запросу» покрывает горячие циклы.

### 4.2 Вывод типов
**Локальный двунаправленный (bidirectional) вывод**, не глобальный HM — жёсткое, непересматриваемое ограничение [D4 §15.2; D3 §8.2: глобальный вывод исторически даёт медленный, плохо инкрементальный тулинг].
- Сигнатуры функций всегда полные (параметры и возврат аннотированы) — интерфейс пакета сериализуем без тел (`.wvi`-файлы, §9.4).
- Внутри тела: режимы *infer* (⇑, синтез типа из выражения) и *check* (⇓, проверка против ожидаемого). Литералы, дженерик-вызовы и лямбды получают типы из контекста check-режима; при недостатке информации — ошибка с просьбой аннотации (никогда — молчаливый дефолт кроме int/float-литералов).

### 4.3 Дженерики и трейты
- Проверка **на месте определения** по trait-bounds (не по месту инстанцирования, как C++-шаблоны) [D4 §12.4; D3 §8.3].
- Мономорфизация в release-бэкенде; в debug/Cranelift-бэкенде разрешён общий (boxed) экземпляр для скорости компиляции — семантика идентична, различие только в кодогенерации (различия ловятся дифференциальным фаззингом [D4 §15.6]).
- Coherence: orphan rule как в Rust (impl разрешён, только если трейт или тип определён в текущем пакете). Специализация — **исключена из v0.1** (Rust не смог сделать её звуковой за 10 лет; не тащим открытую исследовательскую проблему в ядро).
- Динамическая диспетчеризация: `Box<trait Ord>` — явный тип трейт-объекта; ключевое слово `dyn` зарезервировано, но синтаксис v0.1 использует позицию типа. Object-safety правила как в Rust (методы с `Self`-по-значению не объектобезопасны) — формализуются в Фазе 2.
- Const-дженерики v0.1: только через `comptime`-параметры функций (`comptime fn matrix(n: usize) -> type`); полноценные const-generics в типах — кандидат на edition 2028 (изучаем реальную потребность, не тащим сложность заранее).

## 5. Модель памяти: ownership + region inference (закрывает открытый пункт №1 из [D4 §15.8])

### 5.1 Базис (без изменений против D4 §12.2)
Единственное владение, move-by-default; заимствования `&T` (разделяемое, иммутабельное) и `&mut T` (уникальное) с правилом эксклюзивности (aliasing XOR mutability) — ядро Rust-модели, чья звуковость не оспаривалась исследованием [D2 §Rust]. Отличие Weave: **времена жизни выводятся, синтаксиса лайфтаймов нет.**

### 5.2 Формализация region inference (рабочий алгоритм для Stage 0-ревью)
Определения:
- **Место (place)** — переменная, поле, элемент, временное значение.
- **Регион ρ(p)** — множество программных точек (по CFG тела функции), где владение места p действительно: от инициализации до move/drop по каждому пути CFG.
- **Заимствование** b = `&p` порождает регион займа L(b) — множество точек, где b жив (классическая liveness, включая передачи b дальше по графу потоков).

Алгоритм по функции (по типизированному HIR c построенным CFG):
1. Построить **граф потоков (flow graph)** G: узлы — места и займы; ребро p→q для каждого присваивания/передачи аргумента/возврата, через которые значение или заимствование перетекает из p в q. Вызовы функций раскрываются **только по сигнатурам** (см. 5.4), не по телам — межпроцедурного анализа нет by design (инкрементальность [D3 §8.2] важнее точности; это же решение D4 §15.2).
2. Конденсировать G по SCC; в топологическом порядке распространить требования регионов: для каждого займа b с источником p требуется `L(b) ⊆ ρ(p)`.
3. Проверить эксклюзивность: в каждой точке, где живо `&mut p`, не живо никакое другое заимствование p и нет доступа к p напрямую.
4. Нарушение `L(b) ⊄ ρ(p)` ⇒ ошибка с обязательной тройкой в диагностике: (а) строка создания займа; (б) строка, где p перестаёт быть валидным (move/drop); (в) строка последнего использования займа. Формат: «this reference may outlive `x`, which is dropped at line N» [D4 §12.2] — диагностика указывает на конкретные строки, никогда на абстрактные именованные лайфтаймы.

Свойства: анализ **интра-процедурный, O(размер тела × число займов)** в худшем случае, инкрементален по определению (пересчёт — только изменённые тела). Это NLL-класс точности (Polonius-стиль «origins as sets of loans»), что достаточно: Rust-практика показывает, что NLL покрывает подавляющее большинство корректного кода.

### 5.3 Что выразимо, а что нет (честные границы)
Не выводимо без аннотаций: структуры, *хранящие* заимствования с разными временами жизни из разных источников. Решение v0.1: **структуры не могут хранить `&T`-поля** — заимствование живёт только в локальных переменных, параметрах и возвратах. Это радикально: убирает 90% случаев, требующих именованных лайфтаймов в Rust, ценой паттерна «struct-view». Компенсации: (а) `Shared<T>` для долгоживущего разделяемого чтения; (б) итераторы/views реализуются компилятором как inline-развёртка `comptime`-генераторов, а не как хранящие ссылку структуры. Если практика Stage 1 покажет, что ограничение чрезмерно, edition-механизм позволит добавить структуры-с-займами вместе с provenance-аннотациями полей — **расширять выразительность назад-совместимо можно, сужать нельзя**, поэтому стартуем с консервативного варианта.

### 5.4 Provenance-клауза сигнатур (замена именованных лайфтаймов)
Для функций, возвращающих заимствование, сигнатура декларирует источники словом `from`:
```weave
fn get<K: Ord, V>(m: &Map<K, V>, key: K) -> &V from m
fn longest(a: &String, b: &String) -> &String from a, b
```
Для `pub fn` клауза обязательна (интерфейс пакета самодостаточен — требование кэшируемости [D3 §8.2]); для приватных функций выводится из тела. Семантика: регион результата = пересечение регионов перечисленных источников. Это изоморфно Rust-лайфтаймам по выразительной силе для функций (каждому именованному лайфтайму соответствует подмножество параметров), но читается как предложение на английском, а не как алгебра `'a: 'b`.

### 5.5 План B (зафиксирован заранее [D4 Stage 0 Risks])
Если stress-тест Stage 0 найдёт незакрываемую дыру звуковости: `from`-клаузы расширяются до явных именованных регионов **per-function opt-in** (`fn f<region r>(...)`), не как обязательный синтаксис всего языка. Триггер отката: peer-review находит класс корректных программ ≥5% реального корпуса, отклоняемых без внятной диагностики.

### 5.6 `unsafe`
Локальный, аудируемый остров [D4 §12.2]: внутри блока разрешены разыменование сырых указателей, вызов `extern`-функций, `unchecked_*`-операции. Сознательно неудобен [D3 §9 Practical conclusion 2]: линтер требует `// SAFETY:`-комментарий над каждым блоком (ошибка сборки в CI-режиме `weave lint --strict`), `weave lint` печатает сводку unsafe-поверхности пакета, реестр показывает её на странице пакета.

## 6. Система эффектов: алгебра капабилитей (закрывает открытый пункт №2 из [D4 §15.8])

### 6.1 Модель
Эффект — это **капабилити** («что код имеет право делать»), не «асинхронность» [D4 §12.3]. Формально: эффекты образуют **лес путей** с отношением ⊑ (потомок ⊑ предок):

```
io ── fs ── fs.Read | fs.Write | fs.Watch
   └─ net ── net.Connect | net.Listen | net.Resolve
env ── env.Read | env.Write
proc ── proc.Spawn | proc.Exec
time ── time.Read | time.Sleep          (time.Read — эффект! детерминизм [D3 §9.6])
rand ── rand.Secure | rand.Fast
unsafe.FFI                              (любой extern-вызов несёт этот эффект)
```

Множество эффектов функции — конечное множество узлов; **предоставление узла предоставляет всё его поддерево** (грант `fs` ⇒ разрешены `fs.Read`, `fs.Write`, ...). Проверка вызова: `Effects(callee) ⊆ Granted(context)` с учётом ⊑.

### 6.2 Пользовательские эффекты и композиция (ответ на вопрос D4: subtyping или независимость?)
**Решение: независимые корни + явная клауза `requires`.** Библиотечный эффект НЕ является подтипом встроенного (иначе алгебра становится решёткой с пользовательскими рёбрами — привет, сложность вывода и непереносимость интерфейсов между версиями библиотек). Вместо этого:

```weave
effect db { Read, Write } requires {net.Connect}
```

Семантика: функция с `!{db.Read}` абстрагирует вызывающего от транспорта; сам пакет `db` внутри имеет право на `net.Connect` только потому, что декларировал `requires`, и это видно в манифесте и на странице пакета в реестре. Аудит «что реально может этот код» остаётся одноуровневым и конечным: транзитивное замыкание `requires` вычисляется пакетным менеджером и показывается при `weave add` [D3 §9.5, Deno-модель, поднятая на уровень типов].

### 6.3 Вывод, полиморфизм, гранты
- Приватные функции: эффекты **выводятся** (объединение эффектов вызываемого). Публичные (`pub fn`): **обязательная декларация** — интерфейс пакета самодостаточен, инкрементальный анализ не заглядывает в чужие тела [D4 §15.3; D3 §8.2]. Компилятор подсказывает выведенное множество в диагностике и через code action LSP («insert inferred effect set»).
- Полиморфизм по эффектам — переменные эффектов в дженериках (уже в грамматике §3):
```weave
fn map<T, U, effect E>(xs: List<T>, f: fn(T) -> U ! E) -> List<U> ! E
```
- Корневой грант: `main` получает капабилити из `[capabilities]` в `weave.toml` (deployment-манифест [D4 §15.3]). Сужение гранта в рантайме структуры кода: блок `with_capabilities({fs.Read}) { ... }` — внутри блока контекст урезан (проверяется статически).
- Чистота: `!{}` — функция без эффектов; `comptime`-код обязан быть `!{}` + спец-эффект `comptime.Emit` (§8): компиляция никогда не читает сеть/ФС — это одновременно герметичность сборки [D3 §9.6] и защита от вредоносных `build.rs`-аналогов [D3 §9.5].
- Паника — **не эффект** (иначе каждая индексация окрашивает всё; паника — не control flow, а отказ инварианта, изолируемый процессом §7).

### 6.4 Trade-off анализ
Рассмотрено и отвергнуто: (а) **полноценные algebraic effects + handlers** (Koka/OCaml 5) — мощнее, но резко усложняет ментальную модель и рантайм (continuations), конфликт с приоритетом №2 и с предсказуемой производительностью; капабилити-подмножество даёт 80% ценности (аудит + песочница) за 20% сложности; (б) **эффекты только на уровне пакета/манифеста** (Deno-стиль) — теряется главная ценность: компилятор не может отклонить вызов `net` из функции парсинга; (в) **монадические эффекты** — function coloring, прямо запрещён [D4 §12.3].

## 7. Конкурентность: процессы, scope, каналы (детализация [D4 §12.3])

### 7.1 Примитив
**Изолированный лёгкий процесс**: собственный стек (растущий сегментированно от ~8 КБ), собственная **куча-регион** (bump-аллокация, освобождается целиком по завершении процесса — освобождение O(1), нет глобального GC). Общего изменяемого состояния между процессами не существует по построению [D4 §12.3, BEAM-урок D2 §Elixir].

### 7.2 Структура — единственная форма конкурентности
```weave
scope {
    let a = spawn { fetch_user(id) }        // Handle<User>
    let b = spawn { fetch_orders(id) }      // Handle<List<Order>>
    render(a.join()?, b.join()?)
}   // scope не выходит, пока все дети не завершены/отменены
```
- `spawn` разрешён только лексически внутри `scope`; хэндл не может покинуть scope (проверяется region-анализом §5 — **одна механика обслуживает и память, и конкурентность**: scope — это регион).
- `detach { }` — единственный способ «спавнить и забыть»: требует эффекта `proc.Spawn`, аудируем линтером и реестром.
- Ошибка/паника ребёнка: scope отменяет остальных детей, ждёт их cleanup и re-raise (поведение по умолчанию); супервизор-вариант `scope supervise { }` доставляет исходы через `Result` без каскада — Erlang «let it crash» [D4 §12.6] как примитив.

### 7.3 Планировщик и отмена
- M:N work-stealing планировщик; блокирующие syscall-ы уводятся в отдельный пул нативных потоков автоматически (процессам не виден, коду не виден — «нет цветных функций» держится на этом инварианте).
- Отмена **детерминированная**: распространяется только через checkpoint-ы (`yield_point()`, автоматически вставляемые на канальных операциях и I/O [D4 §12.3]). Отменённый процесс синхронно выполняет свои `on_cancel { }`-блоки в порядке LIFO вложенности **до** unwind scope. Формальная семантика порядка cleanup при вложенных scope + панике — deliverable Фазы 2 (исторически самое сложное место, [D4 Stage 2 Risks], бюджетируем как в Java Structured Concurrency JEP).

### 7.4 Каналы и передача данных
- `channel<T>(capacity)` — типизированный, bounded (backpressure по умолчанию; unbounded — только явный `channel_unbounded`, линтер предупреждает).
- Отправка — **move**: значение покидает кучу-регион отправителя. Для больших иммутабельных данных — `Shared<T>` (атомарный refcount, глубоко иммутабелен по типам — единственный тип, живущий вне процессных куч; гонки исключены иммутабельностью, а не дисциплиной).
- `select`-выражение над несколькими каналами — `match`-подобный синтаксис, честная (fair) семантика, специфицируется в Фазе 2.

## 8. Ошибки, паники, comptime (подтверждение D4 §12.5–12.6 + уточнения)

- Двухуровневая модель без изменений: `Result<T, E>` + `?` с автоконтекстом (source location в цепочке ошибки бесплатно, `? context("...")` — опционально) [D4 §12.4]; `panic` разматывает **только текущий процесс** [D4 §12.6].
- `comptime`: тот же язык, тот же дебаггер [D4 §12.5]. Уточнения Фазы 1: comptime-исполнение **детерминировано и герметично** (`!{}`+`comptime.Emit`, §6.3), лимитируется топливом (fuel) с внятной диагностикой вместо зависшей компиляции; `emit` генерирует типизированный HIR (не текст!) — ошибки в сгенерированном коде указывают на emit-выражение и на сгенерированную сигнатуру одновременно (прямой ответ на «errors point into generated code» [D2 §Rust]).
- Рефлексия — comptime-only по умолчанию; `dynamic`-капабилити для рантайм-рефлексии сериализаторов [D4 §12.5].

## 9. Архитектура компилятора `weavec`

### 9.1 Ключевое решение: query-based (запросная) архитектура с первого прототипа
[D3 §8.2–8.3, Practical conclusions 2 и 5; D4 Part 11 №4]. Компилятор — это **база данных запросов** (модель Salsa/rustc-queries): `parse(file) → AST`, `interface(package) → .wvi`, `typecheck(item) → HIR`, `mir(item)`, `codegen(unit)`. Каждый запрос мемоизируется с отпечатком входов; LSP и batch-компилятор — два фасада одной и той же базы. Это не оптимизация, а конституция: батч-компиляция = «прогнать все запросы», IDE = «прогнать запросы под курсором». Ленивая пофункциональная переоценка на каждое нажатие [D4 §12.10] следует из архитектуры, а не героизма.

### 9.2 Пайплайн IR (решён до парсера, [D3 §7 Practical conclusion 2])
```
source ──lex──▶ tokens ──parse──▶ AST (полный, с trivia — нужен fmt/doc/LSP)
      ──desugar+resolve──▶ HIR (типизированный; здесь region- §5 и effect- §6 проверки)
      ──lower──▶ MIR (CFG, moves/drops эксплицитны; юнит инкрементальности = item)
      ──▶ Cranelift IR (debug/test/comptime-JIT)      [Stage 1]
      ──▶ MLIR → LLVM (release; GPU-диалекты)          [Stage 3]
```
- Два бэкенда обязательны [D3 §7 conclusion 1]: Cranelift — секунды компиляции + формально верифицированный lowering [D3 §7.3]; LLVM/MLIR — пиковая производительность + PGO + кросс-компиляция «из коробки» (все таргеты в одном бинаре, Zig-модель). MLIR выбран над «чистым LLVM» ради GPU-диалектов [D4 §12.12] и будущих доменных оптимизаций; цена (сложность) оплачивается только в release-путях.
- `comptime` исполняется JIT-ом через Cranelift (не отдельным интерпретатором — одна семантика, один кодоген, меньше поверхности расхождений; медленный старт компенсируется мемоизацией comptime-запросов).
- Парсер — рекурсивный спуск, **устойчивый к ошибкам** (error-resilient: любой байтовый мусор даёт AST с error-узлами — LSP работает в недописанном коде), диагностики с may-fix предложениями. Формат диагностик — стабильный JSON (контракт для IDE/CI) + человеческий рендер.
- Воспроизводимость — release-blocking CI gate со Stage 1 [D4 §15.7]: битовая идентичность на двух машинах; любой недетерминизм — баг компилятора [D3 §9 conclusion 5].

### 9.3 Инкрементальность и параллелизм
Единица инкрементальности — item (функция/тип); отпечаток = хэш (нормализованный AST + `.wvi` зависимостей). Изменение тела функции инвалидирует только её MIR/codegen; изменение **сигнатуры** — зависимых по интерфейсному графу. Параллелизм: запросы независимых item-ов исполняются на пуле потоков; распределённая компиляция = шардирование codegen-запросов по content-hash (дизайн в Фазе 3, протокол кэша — content-addressed, тот же примитив, что в пакетном менеджере).

### 9.4 Интерфейсные файлы `.wvi`
Публичная поверхность пакета (сигнатуры + эффекты + provenance + comptime-экспорты) сериализуется отдельно от тел [D4 §12.7]. LSP держит в памяти `.wvi` всех зависимостей и тела только открытых файлов — целевые sub-100ms на 10k-строчном коде [D4 Stage 2 Exit criteria] достигаются конструкцией.

## 10. Runtime, stdlib, toolchain (подтверждение D4 + границы Фазы 1)

- **Runtime**: планировщик §7.3, регионные аллокаторы, panic-unwind per-process, без глобального GC. Бинарь — статически слинкованный по умолчанию (деплой Go-класса).
- **Stdlib**: «batteries included» [D4 §12.9], каждая сигнатура несёт эффекты (§6), крипто — только биндинги к аудированным библиотекам, никогда самописное [D4 Stage 4]. Полный API — Фаза 4. Прикладные пункты ТЗ (GPU compute, AI-интерфейсы, статистика, контейнеры, облака) распределяются: core/io/net/json/crypto/testing — stdlib; GPU/ML-основы — официальные foundation-пакеты поверх `gpu`-блоков (не в stdlib v1.0: скорость эволюции ML-API несовместима с LTS-гарантиями stdlib — урок Python: экосистема, а не стандартная библиотека, место для быстро движущихся доменов).
- **Toolchain**: один бинарь `weave` (build/run/test/bench/fmt/lint/doc/add/publish/lsp) [D4 §12.10]; `weave fmt` без конфигурации; установщик `weave-up`; `weave.toml` + content-addressed lockfile; реестр `weave.dev` — foundation-владение, зеркалируемость, без кода при установке [D4 §12.9]. Детали протокола — Фаза 5.
- **Editions** раз в два года, все поддерживаются одним тулчейном, интероп через границу editions [D4 §12.11]. Governance: foundation с уставом до того, как экосистема станет ценной [D4 Part 11 №5]; RFC-процесс со Stage 0.

## 12. Безопасность: сводная модель угроз Фазы 1

| Класс угрозы | Механизм Weave |
|---|---|
| Memory unsafety (UAF, OOB, double-free) | ownership + regions §5; unsafe — локальный остров |
| Data races | процессная изоляция §7 + иммутабельный `Shared<T>`: исключены конструкцией |
| Supply chain: код при установке | запрещён протоколом реестра [D4 §12.9] |
| Supply chain: hijack/unpublish | content-addressed пакеты, hash в lockfile |
| «Что может эта зависимость?» | эффекты §6 + транзитивный `requires`-аудит при `weave add` |
| Trojan source / homoglyphs | лексер §2.1 |
| Недетерминизм сборки | герметичный comptime §6.3 + воспроизводимость как CI-гейт |
| Ошибки самого компилятора | верифицированный lowering (Cranelift-прецедент) + дифференциальный фаззинг двух бэкендов + постоянный LLM-assisted review [D4 §15.6] |

## 13. Инженерный аудит Фазы 1 (self-review)

Проверки согласованности, выполненные перед публикацией документа:
1. **Регионы × конкурентность**: scope-как-регион (§7.2) требует, чтобы region-анализ §5 видел `spawn`-хэндлы как места с регионом ⊆ scope — совместимо: `Handle<T>` — обычное значение, чей регион ограничен блоком scope; отдельного механизма не нужно. ✅
2. **Эффекты × инкрементальность**: вывод эффектов приватных функций мог бы сломать кэш `.wvi` — не ломает: `.wvi` содержит только `pub`-поверхность, где декларация обязательна (§6.3). ✅
3. **Запрет `&`-полей в структурах (§5.3) × stdlib**: итераторы обязаны быть comptime-развёрткой, не хранящими ссылку структурами — зафиксировано в §5.3; API-дизайн итераторов — критический пункт Фазы 4, помечен. ⚠ (отслеживается)
4. **comptime-JIT через Cranelift × кросс-компиляция**: comptime исполняется на host-таргете, эмитит платформонезависимый HIR — расхождения host/target (размер usize) решаются как в Zig: comptime-известные значения типизируются от target. Уточнить формально в Фазе 2. ⚠ (отслеживается)
5. **Строковая интерполяция (§2.3) × приоритет «один способ»**: интерполяция — единственный способ форматирования (нет отдельного printf-мини-языка); спецификаторы формата `{x:.2}` — синтаксис Фазы 2. ✅
6. **Никакой пункт не противоречит обязательным решениям D4** — проверено построчным сопоставлением с Part 11–12. Единственные два *ужесточения* против D4: запрет `&`-полей структур (§5.3, консервативный старт с задокументированным путём расширения) и checked-arithmetic в release (§4.1) — оба расширяемы назад-совместимо, оба обоснованы приоритетом №1. ✅
